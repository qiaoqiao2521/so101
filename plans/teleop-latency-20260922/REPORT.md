# SO101 主从迟钝：诊断结论（2026-09-22）

## 结论与边界

已确认代码中存在“串行逐个读舵机 → 实际帧率下降 → 每帧限幅进一步拖慢追赶”的放大机制；历史日志确实有12Hz/12raw的慢配置。当前默认已是30Hz/48raw，不能断言当前机械臂仍使用旧配置。网页另有独立的3秒刷新延迟。

本机无8765/8766服务监听、无/dev/serial/by-id，未连接或控制硬件；此次不能确认USB响应实际耗时、舵机速度/供电或当前运行参数。没有修改产品代码/配置，没有重启/烧录/推送。

## 证据

1. `mint_follower_demo/app.py:1246` 通过6次顺序read_word取得主臂位置，不是一次批量读。1648读主臂、1701写从臂、1715起周期性读从臂都在同一循环，慢反馈延迟下一帧。30Hz总预算约33.3ms；6次各5ms已经消耗约30ms，尚未计入写入和反馈。具体设备每次是否5ms仍需实测。
2. `app.py:1676` 限制每帧目标步长，速度上限随实际帧率变化。480raw变化在12Hz/12raw下约需40帧/3.3秒，在30Hz/48raw下约10帧/0.33秒；这是目标命令斜坡估计，不是实测机械响应。
3. 旧日志run-20260624-163206.jsonl请求12Hz/max_step12，结束记录333帧/28.66秒≈11.62Hz。多个6月24日会话约11.3–11.8Hz；它们不是9月22日现场数据。
4. 当前serial_config.json为1Mbps、read/write timeout150ms、请求30Hz、反馈5Hz、多数步长48、alpha0.75。`static/app.js:1552` 前端又显式传30/48，覆盖后端默认；单改配置文件不保证UI启动使用它。
5. `static/app.js:2324` 每3000ms请求状态；逐帧跟随在后端进行。因此UI慢不能证明通信慢。普通关节状态缓存也未在每次teleop反馈时同步更新，可能额外显旧。
6. `app.py:1719` 吞掉从臂反馈异常并沿用旧值，1746清空last_error：有失败时可能看起来只是“迟钝”。不是已经证实设备触发。
7. POSIX read的150ms是最大等待，不是正常包固定等待；不得用“6×150ms”推断正常每帧900ms。缺包/超时才另当别论。0.8秒串口settle和夹爪启动hold主要影响开始阶段，不是每帧延迟。

## 离线验证

- 原有4项fake-bus回归通过；不代表实机达30Hz。
- 本目录offline_probe.py调用实际总线类、替换为FakeSerial：6舵机确实6次事务。人为每次延迟0/5/15ms时，一轮分别约0.35/30.48/90.62ms。
- 实际NativePosixSerial.read读取已就绪的OS pipe：150ms超时配置下8字节读取约0.023ms；没有打开串口。
- 上述计时是合成机制验证，不是USB或机械臂测量。

## 下一步（不先提速或放宽限幅）

连接主从臂后先确认实际运行的是当前主线，再采集现有teleop.timing：requested_frequency_hz、leader_read_ms、write_ms、follower_read_ms、active_step_raw_by_joint；用两次状态的Δframes/Δtime计算真实频率。代码当前actual_frequency_hz为瞬时频率平滑值，反馈频率为请求值推导，不能直接当总吞吐率。

若主臂读占大头，再处理逐个读的串口往返；若从臂反馈形成周期性尖峰，再处理反馈安排和串口所有权；若只界面慢，处理状态刷新与缓存。任何运动提速或限幅修改均需独立确认安全边界，不能靠加大步长掩盖I/O阻塞。
